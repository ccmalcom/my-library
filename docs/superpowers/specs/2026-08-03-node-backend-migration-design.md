# Node backend migration — design

**Date:** 2026-08-03
**Status:** approved design, pending implementation plan

## Why

Chase wants a TypeScript backend long-term (one language across the stack) and wants the
backend folded into the Next.js app on Vercel — one codebase, one deploy, $0 hosting.
The Railway Python service stays alive on a paid month during the migration so the two
backends can be benchmarked side by side against the same Supabase database and account
before Python retires.

This is a port, not a redesign: every locked decision in CLAUDE.md carries over unchanged
(CSV-only ingest, import-once ownership, two-stage recommender, metadata-driven profile,
enrichment confidence, evals later). Behavior parity with the FastAPI backend is the
acceptance bar for every route.

## Decisions (settled during brainstorming)

- **Shape:** backend becomes Next.js route handlers on Vercel — no standalone server.
- **Sequencing:** strangler, route by route, in six waves; app fully working throughout.
- **Both backends live simultaneously:** same Supabase Postgres + auth; an admin-only
  switcher flips the frontend between the Railway URL and same-origin `/api/*`.
- **DB layer:** Drizzle ORM over postgres-js; schema generated by `drizzle-kit pull`
  introspection. **Alembic remains the only migration authority until cutover** — new
  tables the Node side needs are added as Alembic migrations.
- **Long-running work:** self-stepping chunked jobs (no Redis, no external queue).
- **Catalog cache:** moves from Railway volume files to a Postgres `catalog_cache` table.
- **CLI:** dropped at cutover, not ported. Web app is the product.
- **Debug mode (new requirement):** admin-toggleable server-side flag enabling structured
  request logs, `Server-Timing` response headers, and admin-gated verbose browser console
  logging. Off = quiet standard logs. Doubles as the benchmark instrument.
- **Cutover:** same-day once wave 5 parity passes (single real user — no soak period).

## Architecture (wave 0 foundations)

Code lives in the existing Next.js app:

- `frontend/app/api/**/route.ts` — route handlers, one group per Python router area.
- `frontend/lib/server/db.ts` — Drizzle + postgres-js client for Supabase Postgres;
  introspected schema checked in.
- `frontend/lib/server/auth.ts` — verifies the same Supabase-issued JWTs (`jose`),
  yielding the same `user_id` values the Python backend uses.
- `frontend/lib/server/crypto.ts` — AES-256-GCM decryption of per-user Anthropic keys,
  **byte-for-byte compatible with the Python format**; proven by a fixture encrypted by
  the Python code.
- `frontend/lib/server/anthropic.ts` — `@anthropic-ai/sdk` wrapper with usage tracking
  (`tracked_create` twin) writing identical `usage_events` rows.
- `frontend/lib/server/ratelimit.ts` — Postgres fixed-window counters (5/min enrich
  start, 30/min catalog search, per user).
- `frontend/lib/server/log.ts` — debug-mode-aware structured logger (request-id, route,
  duration, status; stack traces in logs, never in responses).
- Backend switcher: frontend defaults to the Railway URL; admin-only toggle flips the
  browser to same-origin `/api/*`. Ships in wave 0.
- `/api/healthz` — unauthenticated liveness route.
- Alembic migration adding `catalog_cache` (and the debug-mode flag storage).

## Wave order

| Wave | Contents |
|------|----------|
| 0 | Foundations above; no user-visible routes |
| 1 | Read-only: stats, book list/detail, profile + traits, profile status, recommendations list, settings/usage reads |
| 2 | Simple writes: rate/review/shelf/favorite/exclude, add book, rec feedback, enrichment correction, directive set/clear, remove book, settings writes (incl. key encryption) |
| 3 | Claude flows: profile build/update, archetype + reveal, directive distill, two-stage recommender, discover/similar; catalog cache goes live — **split into 3a/3b/3c during planning, see below** |
| 4 | Jobs + imports: enrichment (self-stepping), CSV/custom imports, exports, purge/delete-account |
| 5 | Admin: invites, usage/feedback browsing, admin config; then cutover |

Per wave: port + parity tests + benchmark, then flip that group's frontend default to
Node. Python remains fallback until cutover.

**Wave 3 split (decided 2026-08-05, during 3a planning).** Wave 3 as scoped above is
larger than waves 1 and 2 combined — `recommend.py` alone is 1,887 lines with a 14-step
retrieval pipeline and six Claude call sites. A single plan would be unreviewable and
would drift during execution, so it ships as three dependent plans:

| Sub-wave | Contents |
|---|---|
| 3a | Catalog client + Postgres cache, `GET /catalog/search`, Claude key resolution + client factory + prompt-parity harness, `POST /directive/draft`, `POST /profile/archetype`, `POST /profile/reveal-lines` |
| 3b | `POST /profile`, `POST /profile/update` |
| 3c | `POST /recommend`, `POST /books/{id}/similar`, `POST /discover` |

Each produces working, shippable software on its own. Waves 4 and 5 are unchanged and
follow 3c.

**Claude-flow parity, defined.** Claude's output is nondeterministic, so end-to-end
response equality is not an achievable bar for these routes. Parity for a Claude flow
means: the prompt string, `system`, tool JSON schema, `tool_choice`, `model`,
`max_tokens`, and message-block structure (including `cache_control` placement) are
byte-identical to Python's for the same DB state, and the handler does identical things
with a given response. Tests assert both via recorded Python prompts and replayed
responses; no test may issue a live Anthropic call.

## Rebrand: ShelfSprite (added 2026-08-04)

The final product name is **ShelfSprite**; the **shelfsprite.app** domain is purchased.
The rebrand splits in two:

- **Domain attach — early, independent of waves** (Chase, dashboard steps): add
  shelfsprite.app to the Vercel project as the production domain; update Supabase Auth
  Site URL + redirect URLs; add the domain to Railway `CORS_ORIGINS` (the frontend still
  calls Railway directly for unported routes). Side benefit: custom domains bypass
  Vercel's SSO deployment protection, unblocking the per-wave benchmark runs and curl
  verification that waves 0–1 had to defer. (DONE)
- **Name rename — at cutover only**: UI copy/titles/metadata, `package.json` name,
  `MYLIBRARY_*` env-var prefixes (env is re-declared at cutover anyway), CLAUDE.md +
  docs, and the `mylibrary.backend` localStorage key (the switcher itself is deleted at
  cutover). Do **not** rename the `mylibrary/` Python package, CLI, or Alembic tree —
  all deleted at cutover, renaming them is wasted work.

## Long-running work

Claude-powered flows (profile, recommend, distill) are single invocations with streaming
and a raised `maxDuration` — they fit within Vercel's fluid-compute limit (~300 s;
**verify exact hobby-plan limit at implementation time**).

Enrichment becomes a self-stepping chunked job reusing the existing `enrich_jobs` table
and polling contract:

1. `POST /api/enrich/start` creates the job row, processes a first batch within a fixed
   time budget (~60 s of rate-limited catalog calls), updates progress.
2. If work remains, the invocation fire-and-forgets a `fetch` to `/api/enrich/step`
   (job id + HMAC job token so the endpoint can't be driven externally) via `waitUntil`.
3. Steps are idempotent (claim only still-unenriched books) → dropped/duplicated steps
   self-heal. A step finding a `running` job untouched past a staleness threshold resumes
   it (replaces `recover_orphaned_jobs` / `fail_if_stale`).

The chain hides behind a small `jobs.ts` interface so a managed queue (Inngest/QStash)
could replace it later without redesign. Debug mode logs every step transition.

**Concurrency:** within a step, catalog requests run concurrently up to the same
requests-per-second budget the Python rate limiter enforces (async I/O, not worker
threads) — the Python loop resolves books sequentially, so this is a headline
opportunity for the benchmark. The same applies to Stage-1 retrieval fan-out in the
recommender. Worker threads are out of scope: the workload is I/O-bound, and a Vercel
invocation has ~1 vCPU; revisit only if profiling ever shows a CPU-bound hotspot.

## Catalog cache

`catalog_cache` table: cache key (source + request hash), JSONB payload, `fetched_at`.
Node catalog client reads through it; entries live indefinitely (book metadata is
stable), shared across function instances, survives deploys. Python's disk cache is
untouched during migration.

## Validation, errors, usage

- Zod schemas mirror the Pydantic models per route group.
- Typed domain errors map to FastAPI's exact wire format — same status codes (409
  duplicate, 400 missing key, 422 validation) and `{"detail": "..."}` bodies — so
  `lib/api.ts` and all components work identically against either backend.
- Usage tracking writes identical `usage_events` rows; spend panel + soft-warn banner
  work mid-migration regardless of which backend made the call.

## Testing

- **Vitest**, three layers:
  1. Unit tests for `lib/server/` modules (crypto fixture encrypted by Python; JWT
     verification against a test JWKS).
  2. Route parity tests per wave: request/response fixtures recorded from the Python
     `TestClient` suite, asserted field-for-field against Node handlers on a real local
     Postgres.
  3. The existing pytest suite keeps running in CI until cutover (it guards the fallback
     backend).
- Claude calls are record/replay in tests — no live spend in CI.

## Benchmarking

After each wave, a scripted pass hits each ported route 30 times on both backends with
real data, recording **warm and cold p50/p95 separately** into `docs/benchmarks.md`,
sourced from debug mode's `Server-Timing`. Stated caveat: this compares
FastAPI-on-Railway-container vs Node-on-Vercel-serverless — deployment shape included,
not language alone.

## Cutover checklist (same-day)

1. All route-group defaults flipped to Node; parity suite green.
2. One manual pass of the main flows on Node only: import → enrich → profile → reveal →
   recommend → feedback → admin.
3. Retire the Railway service (capture env vars first).
4. Final schema snapshot becomes Drizzle's baseline migration — schema ownership
   transfers from Alembic here and only here.
5. Delete `mylibrary/` package, pytest suite, CLI, Alembic tree.
6. Update CLAUDE.md + docs to the single-codebase reality.
7. Rebrand to **ShelfSprite**: UI copy/titles/metadata, `package.json` name,
   `MYLIBRARY_*` → `SHELFSPRITE_*` env prefixes, docs (see "Rebrand: ShelfSprite"
   section — the shelfsprite.app domain attach should already be done by now).

## Out of scope

- Porting the CLI (dropped at cutover).
- Any recommender behavior changes (e.g. Stage-1 matching semantics) — parity only.
- Evals (later phase, unchanged).
- Multi-region/scale work; invite-only single-user scale assumptions hold.

## To verify during planning (not open questions — verification tasks)

- Exact Vercel hobby-plan max function duration with fluid compute (design assumes
  ≥ 300 s is available for Claude flows; if lower, streaming keeps connections alive and
  the profile/recommend flows chunk the same way enrichment does).
- `drizzle-kit pull` fidelity against the current Alembic schema (JSON columns, enums).
